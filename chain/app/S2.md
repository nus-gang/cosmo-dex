# S2 두 자산 원장과 snapshot

[NUS-37](/NUS/issues/NUS-37)의 Chain 구현. 승인 계약 [NUS-36](/NUS/issues/NUS-36)
head `3571c3a331a169a8eef231aad14f7816908dd2c5`에서 분기했다.
계약 hash `2e103517c344f21c2b97fbe7e977f0e614c32c704b0f54978c5bb1fb3ae6ab0f`,
profile hash `70281595d471947a56d9bf8a97553dd388a85b107c215a95cc6f34ea9f5f321f`를 고정한다.

## 실행

Go 1.26.5, SDK v0.55.0, CometBFT v0.40.0 및 기존 go.mod/go.sum을 유지한다.
S1 기본 명령은 그대로다. S2는 모든 명령에 `--network s2`를 지정한다.

```sh
cd chain/app
sh scripts/build.sh
bin/nusd init --network s2 --home .runtime/s2/node --operator-accounts config/operator-accounts.json
# 위 출력의 실제 genesis_hash 사용
bin/nusd start --network s2 --home .runtime/s2/node --genesis-hash <hash>
bin/nusd snapshot --network s2
bin/nusd tx --network s2 --user 0 --denom DEVBASE --op deposit --amount 10000000 --request-id <64hex>
bin/nusd tx --network s2 --user 1 --denom DEVQUOTE --op deposit --amount 100000000 --request-id <다른64hex>
bin/nusd snapshot --network s2 --height <확정높이>
```

기본 home은 S1 `.nus-s1`, S2 `.runtime/s2/node`다. 이미 초기화된 home의
init은 거절한다. start는 실제 genesis bytes의 SHA256과 network/chain ID를 검사하고,
저장 DB의 genesis 및 network를 다시 검사한다. S1 DB 자동 업그레이드는 없다.
CLI init은 단일 검증인 시험용이다. 4검증인 통합 genesis 배치는 SRE의 F 업무에서 수행한다.
임의 초기 C 주입은 제공하지 않는다. 두 등록 사용자의 자산별 bank 초기액은
각 10^12 atoms, C/epoch는 0이며 가스만 운영 주소 4개에도 배분한다.
합의/P2P는 기존 Ed25519, 사용자 TX는 실제 ML-DSA-65 DIRECT다.

## 상태와 소비 계약

- DEVBASE/DEVQUOTE만 예치·출금한다. DEVGAS는 가스 전용이며 같은 경로로 예치하지 못한다.
- 잔고는 owner/asset, epoch는 owner 공통이다. BASE 출금도 QUOTE의 구 epoch 요청을 거절한다.
- bank 이동·C 변경·epoch 증가·receipt는 SDK message cache의 동일 TX 안에서 처리한다.
  메시지 거절 시 경제효과는 롤백되지만, S1과 같이 유효한 ante의 가스/sequence 효과는 남을 수 있다.
- receipt ID는 owner 내 자산 공통이다. 동일 본문을 새 sequence로 재서명하면 원 receipt를
  반환하며 중복 이동/epoch 증가가 없다. 다른 자산/본문이면 ID_CONFLICT다. 원 TxRaw replay는
  SDK sequence 검증에서 거절한다. 직접 출금에 Exchange 허가를 요구하지 않는다.
- 각 자산의 C 합=모듈 보관량, 모든 bank 합=고정 genesis 공급을 검산한다.
  DEVGAS 공급과 bank 합도 별도로 검사한다.
- 기존 ABCI `/nus.exchange.v1.Query/Snapshot`은 S2 실행에서 승인된
  `ChainSnapshot` envelope를 반환한다. S1에서는 기존 JSON 형태를 보존한다.
  요청에 H를 지정하면 H의 등록키·sequence·C·epoch·시장·공급을 함께 읽는다.
- H의 hash/time을 EndBlock에서 H state에 보존한다. 과거 조회에 최신 header를 섞지 않는다.
  accounts는 raw owner순, 자산은 denom순이다. snapshot_id는 승인 JSON frame의 SHA256이다.
  상태 증명/light client 검증이 아니며 신뢰하는 로컬 RPC 경계다.
- 소비자는 ABCI response height=요청 H와 block H의 chain/hash/time, 고정
  genesis/contract/config/version/owner 집합을 대조하고 원시 응답을 보존해야 한다.
  누락된 H, 역행, 불일치는 접수를 닫는 사유다. 관측 신선도·연속 cursor는 C/D 업무가 맡는다.
- SDK 재시작 직후 첫 새 블록 전에 latest 조회가 실패할 수 있다. 빈/0잔고로 치환하지 않는다.
  보존된 과거 H는 블록 진행 후 동일 snapshot으로 재조회한다.

S2 시장은 genesis 초기화 시 고정되며 설정 변경 TX는 없다. 0bps 기본 프로필이다.
25bps 산술·부정 fixture는 공통 계약에 유지되며 이 binary에 실행 중 fee 변경 기능은 없다.
정산·잠정 D/P·엔진 예약·화면은 이 컴포넌트가 구현하지 않는다.

## 검증

```sh
NUSD_BINARY="$PWD/bin/nusd" S2_EVIDENCE_DIR=/tmp/s2-unit go test -mod=readonly -race ./...
python3 scripts/s2-smoke.py --binary bin/nusd --output /tmp/s2-comet
python3 scripts/s2-snapshot-check.py /tmp/s2-comet/final-snapshot.json
python3 scripts/smoke.py --binary bin/nusd --operator-accounts config/operator-accounts.json --output /tmp/s1-regression
```

smoke는 유한 시험이며 종료 시 노드를 정리한다. raw ABCI/header, 실제 TX 응답,
실제 genesis, snapshot, node logs를 보존한다. 단일 검증인 시험은 4검증인 S2-AT01,
통합 S2-AT09, 실제 정산 T04, 분산 내구성 T08/T10 전체 PASS가 아니다.
처리량·운영 SLA는 측정하지 않았다. 전체 T01~T16 full PASS 0/16 기준은 유지한다.
