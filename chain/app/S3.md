# S3 체인 정산 인계 — NUS-55

`nus-s3-dev-1`의 실제 SDK 메시지, C 원장, 영속 COMMITTED/VOID 영수증이다. 승인 선행은 NUS-54 head `0915375cac360f83d62a70587a0e7cf9c89604a1`, tree `ad98a57e149b861369f7d716aed8fd0325aef4f8`다. `protocol/s3` 및 상속 계약·fixture는 수정하지 않는다. 현재 후보의 정확한 commit/tree·시험 원문·최종 판정은 [NUS-55](/NUS/issues/NUS-55)의 첨부와 work product에서 고정한다.

## 실행과 버전

Go **1.26.5**, Cosmos SDK **v0.55.0**, store/v2 **v2.0.0**, CometBFT **v0.40.0**, CIRCL **v1.6.3**을 유지한다. `go.mod`에는 상속 `../contract`를 재사용하는 로컬 module require/replace만 추가했다. 외부 버전과 `go.sum` 변경0. 이 module graph 변경도 CTO 검토 대상이다. SDK·Comet은 해당 태그의 Apache-2.0, Go와 CIRCL은 BSD 계열이며 상속 LICENSE 원문과 이번 manifest의 파일 해시로 추적한다. SDK enterprise 패키지는 사용하지 않는다.

```sh
cd chain/app
export GOTOOLCHAIN=local
sh scripts/build.sh
go test -mod=readonly ./... -count=1 -json > app-tests.jsonl
NUS_S3_COMET=1 NUS_S3_EVIDENCE_DIR="$PWD/bin/s3-evidence" \
  go test -mod=readonly . -run '^TestS3CometLocal$' -count=1 -json > comet-tests.jsonl
python3 scripts/verify-s3-evidence.py bin/s3-evidence > reconciliation.json
```

Go 1.26.5를 PATH에 둔다. 두 개의 독립 `-trimpath -buildvcs=false` 빌드와 동일 buildCommit을 사용해 binary SHA256을 대조한다. generated protobuf는 protoc29.3 + gogoproto1.7.2로 `scripts/generate-s3-proto.sh`에서 재생성한다. Go codec은 canonical BatchV2의 V1 공통 layout만 재사용하며 version/ID/HASH 도메인은 V2로 별도 검사한다.

`TestS3CometLocal`은 `.runtime/s3/`에 매번 새 4개 node home과 무작위 ML-DSA 사용자2·operator2·admin1, Ed25519 합의키를 만든다. loopback 포트만 열고 종료 시 노드·DB를 닫으며 임시 home을 제거한다. private key를 증거에 기록하지 않는다. 실제 원문 genesis와 RPC `/block`, `/block_results`, 원 TxRaw만 증거에 넣는다. 고정 공개 seed를 쓰는 SDK 단위 시험은 이 무작위 runtime과 구분한다.

외부 F 환경은 별도 S3 genesis/home으로 `nusd start --network s3 --home .runtime/s3/node0 --genesis-hash <실제 파일 SHA256>`를 사용한다. 기존 S1/S2 init/공개 키 CLI로 S3 계정을 만들지 않는다. S3 `init`은 단일 검증인 생성 대신 오류를 반환한다. genesis는 initial_height1, 서로 다른 Ed25519 검증인4(양의 power, 시험 driver는 각10), max_bytes1048576, max_gas20000000, evidence.max_bytes65536이어야 한다. `app_state`의 required 필드는 다음과 같다.

| 필드 | 값 |
|---|---|
| `public_keys` | 새 등록 사용자2..16명의 ML-DSA65 raw1952 base64 배열 |
| `settlement_operator_public_keys` | 현재/후임 operator raw1952 두 개; 최초 것은 epoch1 |
| `admin_public_key` | 별도 raw1952 |
| `fee_bps` | 문자열 `0` 또는 `25` |
| `contract_hash` | `6191a54e268a658e4105943f5d1b28a20c550215cfe51f22b80f1cf74cf4a632` |
| `config_hash` | 0bps `eba02241192cd666104d8767e96203a97d089026b3025e2a3241c9638ebdcb9b`; 25bps `f8ff238d7c49661f958db397855e951a483c5496dac0511b82b55fa3bd4e900d` |

역할 간 키 중복을 거절한다. 사용자 bank는 자산별10^12 atoms, 모든 signer GAS10^9 atoms, C/E는0이다. 실제 예치만 C를 만든다. fee 프로필 변경은 새 genesis다. 시작 시 persisted genesis hash와 chain ID를 대조하며 이전 DB 마이그레이션은 제공하지 않는다.

## D/F 연결 API

추가 protobuf는 `proto/nus/exchange/s3/v1/tx.proto`다. 승인 `protocol/s3/messages.proto`와 같은 필드/tag에 Go package·Msg service만 추가했다. 모든 TX는 ML-DSA65 `SIGN_MODE_DIRECT`, 한 message·한 signer다. memo/extensions/tip/feegrant/unordered를 거절한다.

| SDK type URL | 권한·고정 gas/fee/timeout |
|---|---|
| `/nus.exchange.s3.v1.MsgSettleBatch` | 현재 operator; 10M/20000 DEVGAS, 비영 timeout |
| `/nus.exchange.s3.v1.MsgCloseBatch` | 현재 operator; 3M/6000 DEVGAS, 비영 timeout |
| `/nus.exchange.s3.v1.MsgRotateSettlementOperator` | genesis admin; 500000/1000, timeout0 |
| `/nus.exchange.s3.v1.MsgRevokeOrder`, `MsgBumpOrderEpoch` | 본인; 500000/1000, timeout0 |
| 기존 `/nus.exchange.v1.MsgDeposit`, `MsgWithdraw` | 등록 본인; 500000/1000, timeout0 |

Settle/close TX 상한139264B, batch131072B, fills8, proofs16, 기타 TX16384B다. worker가 관측H+8 timeout과 min expiry 여유12·시도3/2·영속 방송 규칙을 적용한다. 체인은 실행h에서 SDK timeout(h>timeout)과 주문 expiry(h>=expiry)를 각각 집행한다. proof는 매 배치 모두 필요하다. PrepareProposal/ProcessProposal/FinalizeBlock에서 같은 ML-DSA count≤34, raw bytes≤1MiB, 선언 gas≤20M을 적용한다.

S3 query `Data`는 **canonical JSON bytes**다(ASCII, key 사전순, 공백0, 정수 문자열). protobuf envelope로 감싸지 않는다. 입력 `context`는 `protocol/s3/schema.json`의 Context 전체이며 `height`와 ABCI RequestQuery.Height가 같아야 한다. `0`은 최신 committed H를 한 번 고정한다. duplicate/unknown key·다른 context를 거절한다. 응답의 ABCI height와 JSON height를 다시 대조한다.

| ABCI path | JSON 입력·결과 |
|---|---|
| `/nus.exchange.s3.v1.Query/Snapshot` | `{context,height}` → ChainSnapshot |
| `/nus.exchange.s3.v1.Query/Batch` | `{context,height,batch_seq}` → BatchLookup; seq>Last이면 NOT_FOUND_AT_HEIGHT |
| `/nus.exchange.s3.v1.Query/Order` | `{context,height,order_hash}` → context/observed_height/order_hash/order; unknown은 order=null |
| `/cosmos.auth.v1beta1.Query/Account` | SDK protobuf QueryAccountRequest → 등록 operator/user의 account_number·sequence·public key |
| `/cosmos.bank.v1beta1.Query/Balance` | SDK protobuf QueryBalanceRequest → operator DEVGAS 등 |
| 기존 `/nus.exchange.v1.Query/Receipt` | 직접 입출금·revoke/bump request receipt. 결과 chain/genesis를 대조 |
| Comet `/block`, `/block_results`, `/tx` | exact TxRaw hash/index·code/gas·과거 확정 조회 |

Order 결과는 `order_wire`, 최초 `signature`(온체인 revoke 최초 binding이면 null), `order_hash`, `settled_qty_lots`, `revoked`다. 온체인 누계이며 엔진 lifetime/pending/corrected 누계를 대신하지 않는다. Snapshot의 terminal_batch_seqs와 owner_events는 해당 H에서 발생한 항목이다. 오래된 슬롯은 Batch로 각각 조회한다. SDK state pruning은 기본 상속 설정이며 **현재 상태의 영구 receipt/SeenFill/order tombstone은 GC하지 않는다**. D의 필요 과거 H 접근에는 F가 충분한 state/block retention을 고정해야 한다.

Comet `/status`가 높이를 보였어도 SDK Commit이 끝나기 전 query는 일시 실패할 수 있다. 기동 준비와 신규 가용액은 성공한 committed query로 판단한다. NOT_FOUND·접수·timeout으로 정산 실패를 만들지 않는다. SDK query는 재시작 직후 메모리 header 대신 높이에 저장된 block identity를 사용해 최초 새 블록 전에도 과거 receipt를 읽는다.

## 보존·rollback·권한

정산은 strict/context/current operator → 과거 슬롯 → seq/prev/operator epoch → 모든 주문 등록키·서명 → binding → owner epoch/revoke/expiry → limit/maker/fee/누계 → C_start gross debit 순으로 검증한다. 다른 fill의 수취액으로 gross debit을 충당하지 않는다. C/T·SeenFill·order binding/누계·LastBatch·receipt는 별도 message cache에서 한 번 적용한다. keeper 전체 store 접근에 read128/256KiB, write96/128KiB 상한을 계측·집행하며 iteration을 금지한다. trace는 `exchange_s3_kv` event다.

실패 message는 exchange 상태 전체가 동일하며 SDK ante GAS·sequence는 별도로 남을 수 있다. 성공 재시도는 최초 receipt/높이/TX hash를 그대로 유지한다. 과거 성공에는 현재 사용자 만료·owner epoch·old operator epoch를 재적용하지 않지만, 현재 operator의 TX 권한은 필요하다. 같은 seq 다른 hash는 conflict, receipt 누락/digest/Last 불일치는 fail closed다.

Close는 미확정 슬롯을 VOID로 소비하고 자산·주문·SeenFill을 바꾸지 않는다. failed_tx_hash/evidence_hash는 감사 참조이며 체인이 외부 실패 proof를 검증한 것이 아니다. **D는 원 settle 확정 실패와 모든 미해소 시도의 종결도 검증해야 정정할 수 있다.** COMMITTED는 close로 뒤집히지 않는다.

성공 출금은 본인 지급과 모든 자산 owner epoch+1을 함께 적용한다. 실패 출금·동일 request 재시도는 추가 epoch 증가0이다. 오프체인 잔량 cancel은 pending 정산을 무효화하지 않는다. Revoke는 원문 hash/owner/epoch/order ID를 영구 바인딩하며, Bump는 전체 주문 epoch를 증가시킨다. admin 회전은 후임 등록키만 허용하고 LastBatch·과거 receipt를 유지한다.

회계는 자산별 module_bank=sum(C)+T+U다. 전체 등록 사용자 C와 개인 bank·module·공급량을 snapshot에서 독립 재합산한다. 양의 잔차는 EndBlock/성공 message에서 U로 격리하고 본인 정상 출금은 유지한다. 음의 잔차는 신규 정산과 해당 자산 출금을 거절한다. T/U sweep·임의 mint/burn 경로는 없다.

## 검증 범위

- 실제 SDK TX: 0/25bps 정상 정산/수취 출금, 정상+위조/초과량/잔고부족 fill 양순서 rollback, C_start 순환 거절, 재시도/과거 seq·conflict/gap/prev, 회전·VOID·revoke/bump, h−1/h/h+1, 두 출금 순서·전액/1atom·같은 block index, LevelDB 재개.
- 최대8 fills/16 distinct proofs 및 기존 binding 재사용: 실제 gas와 전체 keeper KV trace. active fee25/U32_MAX cap·max q/p·U64_MAX expiry와 split ceil 경계.
- 상태 결함 주입은 별도 query cache에서 초과/부족 custody·U128 credit overflow·epoch overflow·receipt 유실/변조를 검사한다. 정상 API에서 만들어진 합의 이력으로 표현하지 않는다.
- 실제 Comet4개: 0/25bps 각3회, fresh random genesis/계정, 확정 block+results 원문·원 TxRaw·receipt·수취 출금·같은 home 재시작·원 확정 TX 조회. Python 별도 정수/해시/보존 oracle과 결함 주입도 실행한다.

시험 driver의 초기 실패(동일 프로세스 node 종료의 indexer DB lock, 종료된 RPC keep-alive, Comet 높이와 SDK 첫 commit 사이 준비 경합)는 원시 로그와 수정 근거를 최종 첨부에 보존한다. 새 private key나 운영자 원문 secret을 로그·artifact로 전달하지 않는다.

B 작성자 검증은 C/D/E 연동, 전체 S3-AT01~09, 브라우저, worker 방송 장애·WAL 정정, 독립 Security G/QA J, 실제 main 인수를 대신하지 않는다. 지속 TPS·분산 복제·성능 SLA·실자산을 검증하지 않았다. CTO→Security 네이티브 검토 후 D가 이 exact candidate를 소비하며 main 병합은 I 단계다.
