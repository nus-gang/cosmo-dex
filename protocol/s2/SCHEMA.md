# S2 schema·hash 세부 규칙

`schema.json`의 `$defs` 이름으로 endpoint별 객체를 검증한다. 모든 정수 문자열의 U32/U64/U128 상한은 regex/자릿수 뒤 실제 정수로 검사한다. raw owner 20B, pk 1952B, signature 3309B, hash/nonce/id 32B를 검사한다. base64는 decode/reencode 일치. 중복 JSON key를 parse 이전에 거절하고 unknown key/null/default를 허용하지 않는다. schema version 문자열은 `1` 고정이다. object 필드 순서는 전송에 무관하나 hash는 아래의 정규화 bytes만 사용한다.

S2 JSON canonical form: object ASCII key 오름차순, 공백 없음, UTF-8, JSON 문자열 escape는 ASCII (`ensure_ascii=true`)이며 `/`는 escape하지 않는다. schema 값은 ASCII와 정수 문자열/bool/null만 사용한다. 수치형 JSON number는 없다. array는 규정 순서를 보존한다. SHA256(frame(domain,canonical_json))이며 frame은 기존 u32be domain length + ASCII domain + u64be body length + body다. 새 JSON 도메인은 `NUS/S2/SNAPSHOT/V1`, `NUS/S2/STATE/V1`, `NUS/S2/RESULT/V1`, `NUS/S2/BOOK/V1`. 기존 ORDER/CANCEL/FILL_ID 도메인은 protobuf를 사용하며 이 JSON 규칙으로 바꾸지 않는다.

- snapshot_id는 `ChainSnapshot.body`만 해시한다. accounts는 raw owner bytes 오름차순으로 정확히 등록된 두 계정, balances/supplies는 denom ASCII순으로 정확히 두 자산, 중복 없음. query 시각/지연은 Observation으로 분리하므로 동일 H의 재조회는 같은 id다. genesis/contract/config hash는 실행 manifest와 일치해야 한다. block hash는 소문자 hex로 정규화한다.
- state_hash는 `EngineState`를 해시한다. 공개 순서와 journal 재생은 같은 schema를 사용한다. 배열에서 account는 raw owner순, order는 admission_seq순, fill은 (command_seq,match_index)순, bindings는 (owner,epoch,id)순, receipt/result index는 state 밖의 WAL 조회 인덱스이며 command_seq순이다. state에는 자기 state_hash/현재 journal record hash/receipt journal_commit_hash/result_hash 인덱스를 넣지 않는다. snapshot의 별도 result index는 WAL과 대조한다.
- result_hash는 `CommandResult`를 해시한다. 원 영수증은 record의 result와 journal index(seq→record hash)를 조합하여 반환한다. receipt 자체를 다시 result에 넣어 hash 순환을 만들지 않는다. 결과/영수증과 최신 view는 분리되므로 과거 성공 결과는 정정 후에도 보존한다.
- JournalRecord.state_json/result_json은 위 두 객체의 canonical bytes를 base64로 저장한다. request_wire/signature는 실제 입력 bytes다. 내부 SNAPSHOT/EXPIRY/CORRECTION에는 request_wire=빈 bytes, signature=빈 bytes 및 그 SHA256을 쓰고 client가 내부 명령을 제출할 수 없게 한다. 내부 command의 request hash는 해당 snapshot/correction JSON hash다. signature_hash는 SHA256(raw signature)이며 Order ID binding hash와 다르다.
- BookSnapshot.content_hash는 content_hash 필드를 제외한 같은 객체를 BOOK 도메인으로 해시한다. bids 가격 내림차순, asks 오름차순; qty는 해당 가격의 live remaining 합이다. 공개 응답에 owner/order_id/signature 없음.
- `FillView`는 내 계정 관점이므로 상대방 owner/order_id는 생략한다. 영속 OutboxFill에는 양측 원본 주문을 참조하고 그 주문에 실제 서명 bytes를 보존한다. 같은 fill ID의 다른 경제 내용은 거절한다.
- OrderView: `max_qty=remaining+filled+cancelled`; `corrected<=filled`이며 corrected는 lifetime filled의 부분집합이다. Filled는 정정 때 감소하지 않는다. 상태는 CORRECTED가 terminal 처리의 최종 표시를 우선하며 상세 원인은 결과에 남긴다. pending_qty=filled-corrected. 기존 취소를 정정하여 살리지 않는다.
- API 페이지 orders<=200/fills<=1000, query `cursor`는 opaque base64이고 owner/genesis/stream_seq에 결합한다. `next_cursor=END`는 끝; 다음 page가 같은 seq를 제공할 수 없으면 409 SNAPSHOT_CONFLICT 후 전체 재조회. 영속 state에는 API 페이지 제한을 적용하지 않는다. 저장 용량 한계면 RESOURCE_LIMIT로 접수를 닫고 데이터를 GC하지 않는다.
- Withdraw prepare/abort 입력은 `LocalAction{request_id}`. 세션 owner와 함께 (genesis,owner,kind,id)로 멱등 binding한다. 서버는 임의 자산 이동을 만들지 않는다. expiry 검사가 없는 로컬 동결 행위이며 요청 원본 JSON canonical bytes를 request_wire 필드에 저장한다.
- LedgerView의 revision/stream_seq는 해당 owner view를 생성한 전역 command_seq. entity revision은 상태 변경마다 1씩, 최초 1. 같은 snapshot 재조회는 증가하지 않는다. 계정 전환 generation은 브라우저의 로컬 비교값이며 server 권한을 대체하지 않는다.

오류 priority: 기존 S0 auth/policy 순서 다음 service freshness/resource gating을 적용한다. 실패한 신규 명령의 retryable=true는 같은 ID 재시도를 허용한다는 뜻이지 아직 저장된 성공을 취소한다는 뜻이 아니다. 원본 receipt가 있으면 현재 stale/만료보다 먼저 반환한다. `errors.json`에 없는 기존 S0/S1 오류는 기존 의미/우선순위로 HTTP422, retryable=false, state=REJECTED; 인증 오류는 401/403. 생성 fixture는 긍정 표현과 부정 경계를 위한 자료이며 임의 클라이언트 snapshot을 허용하는 endpoint가 아니다.
